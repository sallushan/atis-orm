ORM SQL function classification
Review date: 1 October 2026
Scope and interpretation
Reviewed every public method declaration in the supplied SqlFunctions.cs (205) and OverQueryPart.cs (5). Each overload has its own entry and an inline comment in the classified C# copies. The original code, XML documentation, attributes, BOM and CRLF line endings are unchanged. Review comments flag existing issues but do not fix them. Original line numbers below refer to the supplied files, not the longer annotated copies.
This is an API-design classification, not a formal proof of semantic equivalence. Category 1 means a natural .NET/C# expression or a short composition of built-in APIs is preferable as the public query frontend. It does not mean arbitrary SQL functions can be run locally, nor that every provider can translate every .NET overload. Preserving an existing SQL Server method's exact behavior can require retaining a category-3 escape hatch even when its ordinary purpose is category 1.
Category 2 means a useful, explicitly specified database operation or query construct belongs in a common provider-neutral API. Support is capability- and version-dependent; the translator may need a query rewrite, not just a different function name. A provider without support should fail clearly. Category 3 means retaining the current SQL Server-specific contract; it does not assert that no other database has a similarly named feature.
Comparison scope: SQL Server, PostgreSQL, MySQL and Oracle, with SQLite treated as a smaller, sometimes extension-dependent provider. No minimum server versions or .NET target framework were supplied. The modern System.Text.Json alternative is marked framework-conditional; it may require a package on older targets. Providers' exact compatibility must be tested against the supported versions.
The supplied sources expose declaration/translation templates, not the complete expression pipeline or project. No compilation, SQL execution or end-to-end translation tests were performed. Classification coverage and byte-for-byte preservation of original code after stripping the added comments were verified programmatically.
Main design recommendations
Use normal string, Math, DateTime, Guid, conditional/coalesce and LINQ APIs for ordinary operations. Use a provider-neutral database/window layer for operations without a natural standard query expression: window functions, statistical/approximate aggregates, date-boundary differences, explicit precision-aware database types and window-clause builders. Keep SQL Server style codes, exact legacy/store-type casts, code-page functions, phonetic/checksum algorithms and security identifiers/permission semantics in the SQL Server provider.
Normalize both ordinary .NET expressions and shared database helpers to semantic query nodes. Render SQL in provider translators; do not put a SQL Server template on a neutral function and assume its SQL text is portable. Validate result type, nullability, grouping/window context, frame, ordering, volatility/evaluation scope and provider capabilities separately from method classification.
Do not automatically delete category-1 scalar aggregate helpers from a custom implicit-group query DSL. Moving Avg(value) to group.Average(...), or a table-valued split marker to Split/SelectMany, changes query shape and needs an explicit rewrite. Keeping a category-2 neutral facade for those shapes is a defensible convenience choice.
Semantic traps to test before migration
- Strings: trailing spaces; UTF-16 code units versus Unicode scalars; NULL propagation; 1-based indices; invalid/clipped ranges; whitespace versus character-set trimming; database collation versus .NET culture/ordinal comparison.
- Numerics: midpoint rounding, negative precision, nullable lifting, promotion/overflow and SQL errors versus .NET NaN/Infinity. SQL floating functions declared as decimal in this file require an intentional result conversion or corrected signatures.
- Aggregates: COUNT rows versus non-NULL values; DISTINCT NULLs; integer AVG versus LINQ Average; empty/all-NULL results; explicit input ordering for string concatenation; output-size limits.
- Dates: calendar boundary count versus elapsed duration; week anchoring; session language; month ends; temporal store precision/range; statement/transaction clock semantics.
- Windows: partition versus frame, duplicate ordering keys, NULL ordering, offset/default restrictions, and absence of a row versus a row containing NULL. Ordered-set percentiles may require a grouped subquery/join when exposed as per-row windows.
- Volatile functions: server versus client execution, per-row versus per-statement evaluation, seeded session state, and whether an expression is safe to cache/fold. Never parameterize a per-row UUID as one captured Guid.
These are categories of tests, not claims that all the listed differences can or should be emulated. Unsupported exact semantics should be rejected or kept behind the explicit SQL Server API.
OverQueryPart.cs and related supporting types
All five public methods are category 2. OverClause, OrderByClause, QueryOrderByPart and OverClauseConfiguration describe common query syntax and can be provider-neutral. The OverClauseConfiguration constructor is infrastructure, not one of the 210 method declarations; its initialization of two lists is not a database function.
The current representation has partitioning and ordering but no frame. Add an explicit frame model such as ROWS/RANGE BETWEEN boundaries and validate it per function/provider. LAST_VALUE over the default ordered frame is not automatically the last value in the whole partition. Also model sort direction per key and explicit NULL ordering where required.
The DatePart enum mixes units for addition, extraction and boundary counting. Treat each operation's allowed units and week/fraction semantics separately. The String_Split_Result attribute embeds the SQL Server function name: remove that provider detail from any neutral rowset result model and let the provider own the mapping.
